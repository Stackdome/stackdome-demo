Built on Axernel

A pull request goes in. A narrated demo video comes out.

WalkThroughPark reads a GitHub repo or PR, boots the app in a sandbox, scripts a demo, records it with voice and captions, and hands back the video. We wrote a prompt, a Docker image and a thin web app. Axernel ran everything in between.

This page shows where each piece lives, with links into the code and into the Axernel console.

Architecture

Where the work happens

The web app never touches a sandbox, a model or a queue. It makes SDK calls to Axernel and reads back events, a validated result and files.

  • Input and output validated against our schemas
  • Secrets injected as env vars and MCP headers, never in prompts
  • Live event stream with resume, file artifacts, per-run cost
The agent

An agent is a contract, not a chat

The app sends JSON that Axernel checks before admitting the run. The agent must submit JSON that Axernel checks before accepting the result. Files it promises are collected for us. The app never parses free text.

Input

{
  "source": "…/stackdome-demo/pull/8",
  "ref": "axernel/walkthroughpark",
  "subdir": "axernel/scratch/todo-app",
  "instruction": "Show me the fix works",
  "maxSeconds": 60
}

A bad link or a wrong duration is rejected with a 4xx before any sandbox starts.

Templates

The sandbox is a Docker image you own

A template tells Axernel which image to start a sandbox from. Ours carries everything that is slow or fragile to install at run time: a browser, ffmpeg, a local text-to-speech voice with its weights baked in, the Argo recorder, and one command, wtp-render, that turns a demo script into a verified video. The agent decides what to show. The image knows how to film it.

0.1.2

Found from the run's own event log: the first render always failed looking for the browser. One line in wtp-render removed a wasted take from every run.

The rule we settled on: tool mechanics live in the image, which takes minutes to rebuild. Guidance that needs iterating lives in the agent's instructions, where npm run setup publishes a new revision in seconds. Six agent revisions and three images got us from first run to good framing.

The SDK

All of it, in one file

Every call the web app makes to Axernel sits behind five functions in web/lib/server/axernel.ts. Routes and UI never import the SDK. A longer map is in docs/sdk-usage.md.

SDK callOur functionWhenWorth knowing
auth.loginlogin()First call, then cachedRenewed once if a call reports an expired token.
sessions.createstartRun()User clicks "Take a walk"Pins the agent revision. The session's name lives in metadata.axernel.title, which the Axernel console reads.
runs.createstartRun()Same requestCarries an idempotency key, so a retry cannot start two paid runs.
runs.eventsstreamRunEvents()While the run is liveResumable with lastEventId. One server-side pump copies events to SQLite; browsers read from there.
runs.getreadRun()Page load and completionThe authoritative status, validated result, token usage, cost and artifact ids.
artifacts.downloaddownloadArtifact()First time a video is playedCached on disk, then served with HTTP Range so the player can seek.

Setup is the same idea turned into a script: one "ensure it exists" function per Axernel resource, safe to re-run. ensureProject · ensureGithubSecret · ensureModelProvider · ensureTemplate · ensureAgent · setup.ts

One run

From a pasted link to a video

  1. queuedInput passes the schema. The run is saved and handed to the worker. The app gets an id back immediately.
  2. preparingAxernel starts a sandbox from the pinned image, uploads its runtime, connects the GitHub MCP server with the project secret.
  3. runningThe agent reads the PR, clones and boots the app, writes a demo script, runs wtp-render. Each tool call streams to the UI's trail and field notes.
  4. completedThe result passes the output schema. Axernel publishes the three files, records tokens and cost, and releases the sandbox.

Why it was quick

What Axernel gave us without being asked

Real isolationThe agent clones and runs strangers' code. It does that in a throwaway sandbox, not next to our app.
Typed resultsThe UI renders a validated object. There is no prompt-output parsing anywhere in the codebase.
Secrets that stay secretThe GitHub token is a project secret bound to an env var and an MCP header. It never appears in a prompt, a run or a log we store.
Revisions and pinningWe changed the prompt six times while runs were in flight. Each session kept the revision it started with.
Durable runsWe rebuilt and restarted the Axernel API in the middle of two runs. Both finished and delivered their videos.
A live, resumable feedTool calls stream as they happen and can be replayed from an event id, which is what powers the trail and field notes.
Files as first-class outputDeclare a filename, get a downloadable artifact. No bucket, no upload code in the sandbox.
Cost per runTokens and dollars come back on the run. The "$0.020" under each video is Axernel's number.
MCP built inThe GitHub MCP server is three lines of agent config, connected before the prompt starts.
Any modelThe model is a provider record. Swapping DeepSeek for another model is a config change, not a code change.
Rough edges we hit, for the platform team
  • The SDK applies its request timeout to the whole event stream; callers must pass a long timeout and reconnect.
  • artifacts.download returns the whole file; there is no stream or Range, so apps cache.
  • Sessions have no title option; the console's convention is metadata.axernel.title, discoverable only from the frontend source.
  • The harness gives the agent its own HOME and drops the image's ENV, which broke Playwright's browser lookup until the render command set it.
  • Contract schemas accept a fixed keyword list (no description); the SDK types do not show that.
  • No run cancellation yet, and a new org starts with no model provider or template.
